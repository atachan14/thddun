# 要件定義(下書き)

2026-11-09 時点の下書き。決まったことと、案・未決を分けて書く。以前の試作(`prototype-v02`)の仕様は参考にするだけ。

## 1. 何をするツールか
**フォルダを1つ指定すると、その中の Topic を読み込み、親子と前提の構造を見せて、編集できるツール。**

- 例: kb(`G:\kb\content`)を指定すれば kb のトピックを、タスク用のフォルダを指定すればタスクを、同じ見た目で扱う。
- 芯は「親子と前提の構造を見えるようにして、編集できること」。それ以外の部分(担当、表示の細部など)は、あとで別の案に切り替えてもよい。
- まずローカル版を作る。使うのは自分と AI。公開版は、あとから同じコアに保存先と入口を足して作る(方針は [README.md](README.md))。

## 2. 用語
| 用語 | 意味 |
|---|---|
| Topic | データの単位。Markdown のファイル1つ。kb のトピックと同じ形。 |
| Card | Topic を画面に描いたもの。表示の言葉で、データの単位ではない。 |
| Workspace | 登録したフォルダ。名前・パス・読み取り専用かどうかを持つ。 |
| 親子 | フォルダの入れ子で表す(kb と同じ)。 |
| 前提 | 先に済ませる Topic。`requires` に書く。kb では「先に読むもの」、タスクでは「先に終わらせるもの」。 |
| 関連 | 構造には効かないつながり。`related` に書く。 |
| 担当 | Topic に付けられるおまけ。担当者と、その人の状態(未着手・進行中・保留・完了など)。 |

名前は Card ではなく Topic に揃える。理由: データの形を kb とそのまま同じにするため。

## 3. データの形(kb と同じ)
- **Topic になるもの:** 先頭の項目に `id` がある `.md` ファイル。子を持つ Topic はフォルダ形式で、本文は `_topic.md` に書く。
- **無視するもの:** `_` で始まるファイルとフォルダ、`id` のない Markdown、Markdown 以外のファイル。
- **先頭の項目:** `id`、`requires`、`related` に加え、kb の `priority` や `updated` など、ほかの項目もそのまま読んで表示できるようにする。
- **担当:** 担当の項目(名前は未定。例: `assignees`)を足すだけ。担当のない Topic は、kb のトピックと同じ扱い。
- **ID:** kb と同じ形(`YYYYMMDD-HHMMSS-xxxx`)。thddun で作る Topic にも、同じ形の ID を付ける。
- **タイトル:** ファイル名(フォルダ形式ならフォルダ名)。

## 4. Workspace
- 登録する項目は、名前・フォルダのパス・読み取り専用かどうか。
- 左の Pane の一覧から選んで切り替える。
- 一覧はパソコンごとの設定なので、リポジトリには入れず、ユーザーのフォルダ側に保存する。
- **前提と関連は、まず同じ Workspace の中だけ。** 将来は、ID を使ってほかの Workspace の Topic も参照できるようにしたい。ID は Workspace をまたいでも重ならないので、Workspace に親を持たせるような構造の強制はしない。

## 5. 画面(最初の版)
1. **ボード:** 今いる Topic の子を Card で並べる。
2. **関係図:** 前提の線で Card を並べる。以前の試作 v0.1 の「前提を右、後続を左に、1段を1列に」が参考になる。
3. **詳細:** 選んだ Topic の本文と、先頭の項目を表示する。
4. **一覧:** 左の Pane に Workspace の一覧を出す。

## 6. 編集(最初の版)
- Topic の作成・名前の変更・親の変更(ファイルの移動)・前提の追加と削除・本文の編集・担当の状態の変更。
- **保存:** ファイルに書き、操作した人を作者にして Git にコミットする(kb と同じやり方)。
- **競合:** 読み込んだ後にファイルが変わっていたら、上書きせずに止めて知らせる。
- **操作する人:** すべての操作に「誰が操作したか」(自分か、どの AI か)を持たせる。
- **権限:** 権限を確かめる入口は必ず通す。ローカル版では全部許可で、読み取り専用の Workspace だけは書き込みを拒否する。

## 7. 技術
- コアは JavaScript(TypeScript を含む)で書く。理由: ブラウザだけで動く公開デモで、同じコアをそのまま使えるため。
- ローカル版は、ファイルの読み書きと Git の操作をするだけの、薄いローカルサーバーにする。
- 今のこの PC は、Node が PATH にない。開発の前に入れる必要がある。

## 9. 案(確定ではない)
- **kb は、まず読み取り専用で開く。** 理由: kb にはコミット時のフックや作者名のルールがあり、thddun から書くには、それに合わせる必要があるため。編集はタスク用の Workspace から始める。
- **前提の循環は禁止する**(以前の試作と同じ)。

## 10. 未決
- 担当のない Topic の完了。状態なしにするか、子が全部終わったら完了とするか。
- 担当がある Topic の完了の決め方。以前の試作では「担当者全員が完了、かつ子と前提も完了」だった。
- タスク用の Workspace の置き場所。Git で管理するフォルダにするか(コミットするなら必要)。
- 担当の項目の名前と、状態の種類。
- `updated` を誰が書くか(kb ではコミット時のフックが書く)。
- 名前(thddun のままか、変えるか)。中身が固まってから決める。
